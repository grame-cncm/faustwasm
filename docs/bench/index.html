Faust in WebAssembly, against native C++

The same Faust programs, compiled to wasm by faustwasm and to C++ by the native Faust compiler, timed under one protocol. Programs without a math function in their sample loop run close to C++. The ones far behind call such a function at every sample, and wasm sends each call to JavaScript. Rewriting them with fastmath.lib closes most of that gap.

How much slower the wasm runs

Time per frame of the generated wasm divided by that of the C++, log scale. Right of ×1 the wasm is slower, left of it faster.

  • calls a math function at every sample (in JavaScript, from wasm)
  • no math call in the sample loop

Why. WebAssembly has instructions for sqrt, floor, abs, min and max, but not for sin, exp, pow or tanh. The Faust wasm backend imports those from the host, and faustwasm gives it Math.sin, Math.exp… Each call leaves wasm and computes in double precision. When a program needs them only to compute coefficients from its controls, the cost is paid once per block and disappears (zita_rev, clarinet). When it needs them at every sample (a waveshaper, an oscillator computing its sine, a compressor converting to dB), it pays a call into JavaScript per sample.

What fastmath.lib changes

The same programs with their per-sample functions taken from fastmath.lib: fa.ftanh, fa.fsin, fa.fsin2pi, fa.flinear2db, fa.fdb2linear. These are written in Faust, with no foreign function, so they compile to plain wasm instructions. Each wasm time is divided by that of the original program in native C++, which uses the C library.

  • wasm, C math functions (JavaScript)
  • wasm, fastmath.lib

The fast tier used here stays within a few ulps of the C library: the outputs of the rewritten programs differ from the originals by −100 dB or less. Faust has no option that makes this substitution: the program calls fa. functions in place of the C ones. -fm is another mechanism, for C, C++ and LLVM, where it replaces calls to the C library with those of faust/dsp/fastmath.cpp. In wasm it only renames the imports, and faustwasm supplies no such functions.

A fastmath.lib function is slower than the C library in some cases: in native C++ the logarithms cost more (compressor_fa is slower than compressor there). The library is meant for the web, and for loops the C++ compiler can vectorize once no call is left in them.

What the Web Audio wrapper adds

Time through FaustMonoWebAudioDsp.compute, the per-block entry point of an AudioWorklet node (input copies, timed events, bargraphs, the non-finite check), divided by the time of the wasm compute alone. Below ×1 is measurement noise: the wrapper does strictly more work.

All numbers

Nanoseconds per frame, best run. Click a column to sort. “max |Δ|” is the largest difference between the wasm and C++ outputs over their first 4096 frames, relative to the peak: it shows both sides computed the same thing (greyhole’s modulated feedback delays amplify a 1e-6 rounding difference over time).

Method

Each program is compiled twice with -ftz 2, the option faustwasm’s createNode uses: to wasm by the libfaust-wasm that faustwasm ships, and to C++ by the native Faust compiler with a minimal architecture file, built with clang -O3 (no fast-math, like wasm). Both render at 48 kHz in blocks of 128 frames (the AudioWorklet quantum), on the same input noise, with every control at its default. After a warm-up run, each side runs 5 timed runs of one second of audio per round, for 3 rounds where the sides take turns, so that a burst of load on the machine does not fall on one side only. The best run is kept. The wasm runs in Node, on V8, the engine of Chrome.

Numbers depend on the machine; ratios travel better than nanoseconds. To measure your own:

git clone https://github.com/grame-cncm/faustwasm && cd faustwasm && npm install
FAUST_SOURCE_DIR=/path/to/faust npm run bench -- --json results.json
node test/bench/report.mjs results.json   # rewrites docs/bench/index.html

The programs are in test/bench/dsp, the bench in test/bench/wasm-vs-cpp.mjs.
