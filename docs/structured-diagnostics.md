# Structured compiler diagnostics

The raw Rust compiler module can return a complete diagnostics-v2 report in
addition to the existing human-readable error message. This report is intended
for editors, build tools, UIs, and LLM clients that need stable codes, source
ranges, typed facts, traces, or suggested edits.

The structured API is additive. Code that only displays `Error.message`
continues to work.

## Handling a failed compilation

Catch `FaustCompilerError` and query the rejected error object:

```ts
import {
    FaustCompilerError,
    type FaustDiagnosticReport,
    type IFaustCompiler
} from '@grame/faustwasm';

export async function compile(
    compiler: IFaustCompiler,
    name: string,
    source: string
) {
    try {
        return await compiler.createMonoDSPFactory(name, source, '');
    } catch (error) {
        if (!(error instanceof FaustCompilerError)) {
            // For example, WebAssembly.compile(...) may reject generated bytes.
            throw error;
        }

        const report: FaustDiagnosticReport | null =
            error.getErrorDiagnostics();
        if (report === null) {
            // Older Rust modules and the historical C++ compiler are text-only.
            console.error(error.message);
            return null;
        }

        for (const diagnostic of report.diagnostics) {
            const primary = diagnostic.labels.find(
                ({ style }) => style === 'primary'
            );
            console.error(
                diagnostic.code,
                diagnostic.stage,
                primary?.range,
                diagnostic.facts,
                diagnostic.fixes
            );
        }
        return null;
    }
}
```

`FaustCompilerError.getErrorDiagnostics()` is authoritative for that one
rejected request. `compiler.getErrorDiagnostics()` is only a convenience for
the most recent failure and can be overwritten when several compilations run
concurrently.

The method takes no diagnostic-level argument. It returns every retained field;
the client can filter the report without forcing the FFI boundary to discard
facts, traces, fixes, related diagnostics, or debug evidence.

Do not parse `Error.message`. It remains a useful display and compatibility
channel, but its wording is not a machine contract. Branch on
`FaustCompilerError`, `schema_version`, `diagnostic.code`, `stage`, and the
typed fields instead.

## Warnings from a successful compilation

Warnings and remarks do not belong to the failure channel:

```ts
const factory = await compiler.createMonoDSPFactory(
    'domain-warning.dsp',
    'process = sqrt;',
    '--warn'
);
const report = compiler.getDiagnostics();

for (const diagnostic of report?.diagnostics ?? []) {
    console.log(diagnostic.severity, diagnostic.code, diagnostic.facts);
}
```

The report has `status: "success"`. It is available after a fresh
Rust-backed compilation when the module supports the success query; a cache hit
or historical compiler path returns `null`.

## JSON contracts and compiler options

faustwasm handles three unrelated JSON payloads:

| Payload              | Purpose                                               | Availability                   |
| -------------------- | ----------------------------------------------------- | ------------------------------ |
| DSP JSON             | UI, inputs/outputs, metadata, and runtime layout      | successful factory compilation |
| Auxiliary-files JSON | transport for generated SVG and other auxiliary files | successful helper request      |
| diagnostics-v2 JSON  | explanation of compiler errors, warnings, and remarks | diagnostic query               |

Use names containing `diagnostics` for the third contract. Do not treat the
factory's DSP JSON as an error report.

`--error-format json` controls the `faust-rs` command-line renderer. It is not a
Faust DSP compiler option and must not be added to
`createMonoDSPFactory(...)` or `createPolyDSPFactory(...)`. faustwasm obtains
the complete report through the dedicated result-handle query.

## Compatibility, schema evolution, and privacy

- A current faustwasm package feature-detects the diagnostics exports. Older
  Rust modules and the historical C++ compiler still reject with their existing
  text message; structured methods return `null`.
- Malformed diagnostics JSON also degrades to `null` and never replaces the
  original compilation message.
- Check `schema_version` before interpreting a report. Version 2 clients should
  ignore unknown fields. The parser preserves them so additive schema changes
  survive the JavaScript boundary.
- Rust FFI reports intentionally set source `text` to `null`. Source names,
  kinds, content hashes, source ids, and half-open byte ranges remain available.
  A client that submitted the source can resolve those ranges locally without
  copying proprietary DSP text or embedded libraries into logs.

## Preparing context for an LLM

Send selected typed fields rather than the human message or the entire source
tree:

```ts
const diagnostic = report.diagnostics[0];
const primary = diagnostic.labels.find(({ style }) => style === 'primary');

const llmContext = {
    schemaVersion: report.schema_version,
    code: diagnostic.code,
    stage: diagnostic.stage,
    primaryRange: primary?.range ?? null,
    facts: diagnostic.facts,
    traces: diagnostic.traces,
    fixes: diagnostic.fixes
};
```

The LLM can use `primaryRange` to request the relevant slice from the client,
reason from typed `facts` and `traces`, and offer only fixes whose
`applicability` matches the client's editing policy.
